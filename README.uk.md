# dal (달) — легкий трекер, що утримує рамку на людині у відео з пошуково-рятувальних дронів

**Вкажіть людину один раз (клік оператора або рамка детектора), і dal супроводжує її кадр за кадром на Raspberry Pi Zero 2 W вартістю 15 $. До нього додано бенчмарк довгого утримання: чи не губить трекер людей.**

З висоти 50–120 м людина займає кілька пікселів, а камера дрона постійно рухається. Детектор може її знайти, але на Raspberry Pi Zero 2 W малому детектору потрібно 0,3–0,6 с на кадр, тож запускати його на кожному кадрі не вийде. **dal** (달, корейською «місяць»; він супроводжує детектор [hae](https://github.com/sashapiscivca-svg/hae), «сонце») заповнює проміжки: отримавши одну рамку, він утримує рамку на цій людині в наступних кадрах, повідомляє, наскільки він упевнений, і повідомляє, коли людину втратив. Його призначення — допомагати пошуковцям підтверджувати знахідки, а не замінювати їх.

Рекомендований трекер — **класичний і без навчання**: кореляційний фільтр MOSSE, фільтр Калмана й компенсація руху камери, кілька сотень рядків numpy та OpenCV. Ми також навчили малий нейромережевий трекер (DalNet зі спайковим модулем руху) і публікуємо його як `dal-n` для досліджень, але **на кожному нашому бенчмарку класичний трекер був щонайменше таким самим точним**, тому типовим є саме він.

> [!IMPORTANT]
> dal — **дослідницький реліз** для **цивільного пошуку й рятування**. Він губить людей і може впевнено тримати рамку на порожньому фоні (див. [Що не доведено](#що-не-доведено)). Він повідомляє лише координати на зображенні: у ньому **немає керування польотом, підвісом чи камерою, геолокації й логіки «слідувати за ціллю»**, і його не можна пов'язувати з автоматизованими діями проти людей. Спершу прочитайте [RESPONSIBLE_USE.uk.md](RESPONSIBLE_USE.uk.md).

## Що робить dal

| | |
|---|---|
| Вхід | кадри відео (сірі або RGB, будь-якого розміру) і одна початкова рамка `(x, y, w, h)` людини, яку треба супроводжувати |
| Вихід на кожен кадр | рамка, впевненість у [0, 1] і ознака `lost` («втрачено») |
| Корекції | `correct(box)` / `correct_from(detections)` приймають нову рамку від детектора без скидання трекера |
| Профілі | `visible` (RGB, напр. люди у воді) і `thermal` (тепловізор), обрані за результатами на відкладених даних |
| Бенчмарки | повнота / точність / F1 на коротких кліпах і **Виживання@N** (довге утримання) з бутстреп-інтервалами довіри |
| Чого немає | ідентифікації, повторного впізнавання між відео, будь-якого керування апаратом, камерою чи підвісом, геолокації |

## Швидкий старт

```bash
git clone https://github.com/sashapiscivca-svg/dal && cd dal
pip install -e .                        # середовище виконання: лише numpy + opencv-python-headless
```

Командний рядок (початкова рамка — `x,y,w,h` у пікселях першого кадру, лівий верхній кут):

```bash
dal track flight.mp4 --init 812,430,22,18 --out tracked.mp4 --json track.json   # профіль обирається за відео: thermal для сірого, visible для кольорового
dal track frames/ --init 812,430,22,18 --profile thermal --ego-scale 0.3          # тека зображень; швидша оцінка руху камери для Pi
dal info                                                                         # версія і профілі
```

`dal track` зменшує кадри так, щоб початкова рамка мала близько 24 px — розмір, під який налаштовано трекер (`--target-px`), і повертає рамки в пікселях оригіналу.

Python:

```python
from dal import make_tracker

trk = make_tracker("visible")              # або "thermal"; будь-який параметр ClassicTracker можна перевизначити
trk.init(frame0, (cx, cy, w, h))           # кадри: uint8 (H, W) або (H, W, 3) RGB
for frame in frames:
    r = trk.step(frame)                    # {"box": (cx, cy, w, h), "conf": 0..1, "lost": bool}
    if detector_ran_on_this_frame:
        trk.correct_from(detections_cxcywh)   # найближча детекція в межах воріт; швидкість лишається, після втрати фільтр перенавчається
```

Для періодичних корекцій від детектора рекомендуємо (попередньо, див. [бенчмарк](docs/benchmark.md#detector-corrections)) `make_tracker("visible", **dal.classic.WITH_DETECTOR)`.

## Результати

Усі числа взято з задокументованих прогонів проєкту (по одному прогону, без перенавчання між ними); протоколи й точні команди — у [docs/benchmark.md](docs/benchmark.md). Трекер ініціалізується справжньою рамкою кадру 0, а далі працює сам. Кадр є **влучанням** за IoU, коли IoU ≥ 0,5, і за **центром**, коли передбачений центр лежить не далі за половину більшої сторони рамки цілі + 2 px від її центра (IoU надто суворий для цілей 6–25 px: на цілі 12 px зсув на 3 px уже знижує його до 0,6). Повнота рахує влучання серед усіх кадрів; точність — серед кадрів, де трекер не оголосив втрату.

### Короткі кліпи: класичний проти навченого

F1 за IoU / F1 за центром, у дужках — частка кадрів, оголошених втраченими. Налаштування обирали на кожному третьому кліпі SeaDronesSee і MOBDrone (решта дві третини, відкладені, привели до тих самих висновків) і на окремих локаціях WiSARD для підбору; рядки WiSARD нижче для підбору не використовувались.

| Набір (кліпів; кадрів) | класичний `v1` (яскравість + Калман) | класичний `thermal` (яскравість, без Калмана) | класичний `visible` (градієнти + Калман) | навчений `dal-n` (чутливий, `lost_thr` 0,03) |
|---|---|---|---|---|
| SeaDronesSee val, люди у воді, сірий (70; 13 312) | **0,778** / 0,931 (0,08) | 0,767 / 0,937 (0,06) | 0,765 / **0,964** (0,02) | 0,734 / 0,913 (0,04) |
| MOBDrone, люди у воді, RGB (119; 33 423) | 0,417 / 0,979 (0,04) | 0,416 / 0,976 (0,04) | **0,472 / 0,997** (0,00) | 0,387 / 0,837 (0,14) |
| WiSARD тепловізор, відкладені локації (20; 2 398) | 0,523 / 0,739 (0,03) | **0,529 / 0,794** (0,04) | 0,474 / 0,701 (0,00) | 0,339 / 0,545 (0,06) |
| WiSARD тепловізор, «складні», відкладені локації (52; 3 843) | | **0,627 / 0,841** | | |

Як це читати:

- **На людях у воді (RGB) класичний трекер тримає центр на людині у 96–99,7 % кадрів.** Градієнтні ознаки (`visible`) найбільше допомагають там, де це важливо, — на найскладніших кліпах: на найгіршій чверті кліпів SeaDronesSee F1 за центром зріс з 0,760 до 0,883.
- **Точність рамки обмежує розмір, а не положення.** Розмір рамки береться з кадру 0; якщо підставити справжній розмір, F1 за IoU зріс би щонайбільше на 0,06–0,20. Оцінка масштабу на відкладених даних не допомогла і вимкнена.
- **Тепловізор значно складніший** (F1 за центром 0,79–0,84). Ознаки, що вигравали на локаціях підбору, програвали на відкладених, тому профіль `thermal` лишився найпростішим.
- **Навчений dal-n жодного разу не обійшов класичний трекер.** З типовим (збалансованим) порогом він має 0,750 / 0,866 на SeaDronesSee val. Його навчено за 1 500 кроків з одним seed, тож це означає «не за такого бюджету», а не «ніколи».

### Довге утримання: Виживання@N

Короткі кліпи не показують, чи не загубиться людина через 20 секунд. **Виживання@N** — частка людей, яких ще утримано без втрати на кадрі N (втрата — ≥ 10 кадрів поспіль, коли центр не на людині), серед треків довжиною не менше N кадрів, з 95 % інтервалами довіри з бутстрепу за послідовностями.

Що ми з'ясували:

- **На RGB-відео над водою трекер утримує людей упродовж усієї довжини наших треків (до 1000 кадрів, 33 с).** З градієнтними ознаками жоден трек MOBDrone не загубився до кадру 500, а p95 похибки центра лишався близько 12 px (0,4 розміру цілі) на 500–1000 кадрах.
- **На тепловізорі приблизно кожна третя людина губиться протягом 100 кадрів**, і більшість цих втрат тихі: трекер і далі впевнено тримає рамку на фоні.
- **Наші власні механізми проти дрейфу не допомогли.** Перевірка вперед-назад, вибір між кількома піками, банк шаблонів фільтра й повторне захоплення не дали приросту Виживання@N хоча б на 1 пункт, тому вони постачаються як вимкнені опції.
- **Допомагають періодичні корекції від детектора**, але тут вони змодельовані зі справжньої розмітки з шумом (верхня межа: без пропусків і хибних детекцій). **Справжній детектор у циклі в цьому релізі ще не оцінено.**

Повні підсумки кожного прогону (дрейф за віком треку, хибні захоплення, повернення) — у [`results/survival_reference.json`](results/survival_reference.json).

### Перевірка опублікованих команд

Щоб переконатися, що цей репозиторій відтворює оригінальний код, ми завантажили 13 валідаційних кліпів SeaDronesSee (`--clips 1-4,33-41`, 1 846 кадрів) і запустили на них `dal bench` та оригінальний дослідницький код. Класичні профілі дали **ідентичні** числа (до 6 знаків): `v1` F1 0,823 (IoU) / 1,000 (центр), `thermal` 0,820 / 1,000, `visible` 0,837 / 1,000, усі з 0 % втрачених кадрів; опублікований ONNX `dal-n` збігся з оригінальною контрольною точкою PyTorch (0,807 / 0,930, 7 % кадрів втрачено). Ця легка підмножина — не повний бенчмарк: на всіх 70 кліпах числа ті, що в таблиці вище. Див. [docs/benchmark.md](docs/benchmark.md#quick-check).

## Як це працює

```
кадр t ──► рух камери: фазова кореляція між кадрами t-1 і t (зменшеними)          ──► (dx, dy)
        ──► прогноз Калмана (стала швидкість, + зсув камери, затухання під час втрати) ──► передбачений центр
        ──► патч 48×48 навколо прогнозу ──► кореляційний фільтр MOSSE              ──► зсув піку + впевненість PSR
        ──► ворота Махаланобіса ──► оновлення Калмана ──► оновлення фільтра (лише коли знайдено) ──► рамка, conf, lost
рамка детектора (необов'язково, кожні K кадрів) ──► correct(): вимір для Калмана / перенавчання фільтра після втрати
```

- **MOSSE** (Bolme et al., 2010) навчає кореляційний фільтр у частотній області на першому патчі й далі адаптує його. Відношення піку до бокових пелюсток (PSR) відгуку — це впевненість; нижче 0,25 від еталона кадр оголошується втраченим.
- **Рух камери** визначається фазовою кореляцією цілих кадрів, без навчання, і зсуває прогноз.
- **Фільтр Калмана** (стала швидкість) згладжує й передбачає. Його налаштування з'явилися з аналізу зривів: слабкий пріор швидкості, обмеження швидкості, ворота і затухання швидкості під час втрати. До цього один хибний вимір міг «відправити» рамку в політ зі швидкістю 15 px на кадр.
- **Профілі**: `visible` додає до фільтра чотири канали орієнтації градієнта (схоже на HOG, лише numpy); `thermal` використовує яскравість і обходиться без Калмана, що найкраще спрацювало на відкладених тепловізійних локаціях.

Подробиці, опції та рішення, що за ними стоять: [docs/architecture.md](docs/architecture.md).

## Навчений трекер (dal-n)

DalNet — сіамський трекер на 36 639 параметрів: спільний backbone корелює шаблон із кропом пошуку, а **спайковий модуль руху** (нейрони leaky integrate-and-fire) читає різницю кадрів і зберігає мембрани між кадрами як пам'ять руху. Він працює в тому самому циклі з Калманом і рухом камери. ONNX-експорт має стан модуля руху як явні входи й виходи, тому працює без PyTorch (`pip install -e ".[onnx]"`):

```bash
dal track flight.mp4 --init 812,430,22,18 --tracker onnx --model models/dal-n
dal bench short data/sds_val --tracker onnx:models/dal-n --kw '{"lost_thr": 0.03}'
```

Чесні висновки: на синтетичних послідовностях спайковий модуль обійшов неспайкового двійника з тією самою кількістю параметрів на 0,022 NWD-AUC (два seed; 0,701 проти 0,679), але двійник має іншу нелінійність, тож це не доводить користі від спайків. На CPU спайки не дають прискорення (0,8 мс проти 0,8 мс на крок). На реальних кліпах класичний трекер був кращим скрізь (таблиця вище). Ми публікуємо dal-n, бо саме порівняння — частина результату; навчальні дані, рецепт і межі — у [MODEL_CARD.md](MODEL_CARD.md).

## Що не доведено

- **Тепловізійні треки — це псевдотреки.** WiSARD має розмітку детекції, а не треки; ми зв'язали рамки між кадрами за перекриттям. Частина кліпів перескакує з однієї людини на іншу, і за тепловізійними числами стоять лише 9–11 незалежних послідовностей (3 відкладені локації). Ручно розмічених довгих тепловізійних треків у відкритих даних, наскільки нам відомо, немає.
- **Малі вибірки, по одному прогону.** Кожне число — один прогін однієї конфігурації. Виживання@N спирається на 16–70 треків; для N = 200 на WiSARD достатньо довгих треків лише 8. Інтервали широкі.
- **Train і val SeaDronesSee зняті на одному озері**, а кліпи MOBDrone з одного відео корельовані (бутстреп групує MOBDrone за відео, але кліпи SeaDronesSee з одного відео вважаються незалежними).
- **Корекції від детектора змодельовані** зі справжньої розмітки з шумом. Справжній детектор пропускає людей і дає хибні тривоги; справжній детектор у циклі в цьому релізі не оцінено.
- **Навчений трекер:** один seed, 1 500 кроків навчання, частково синтетичний навчальний набір (патчі людей, вставлені на реальні фони). Порівняння спайкового й неспайкового модулів — лише на синтетиці.
- **Час на Pi** виміряно для трекера до прискорення оцінки руху камери, на одній платі без радіатора; повний крок трекера після прискорення та енергоспоживання не вимірювали.
- **Не оцінювали:** людей на суші в RGB, натовпи й перетини людей, нічне RGB, сильний дощ чи туман, цілі менші за 6 px, частоту кадрів, відмінну від 30 к/с, радіометричний тепловізійний вхід.
